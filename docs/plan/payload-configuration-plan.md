## 1. Inventory

| # | Figma page | Payload entity | Why |
|---|---|---|---|
| 1 | **Strona główna** | **Global** (`Homepage`) | One document, no slug CRUD, no list view needed. Singleton with blocks. |
| 2 | **O mnie** | **Global** (`AboutPage`) | One document, single photographer biography, no meaningful slug-based routing ergonomics. |
| 3 | **Galeria** | **Global** (`GalleryPage`) | One gallery-index page — it's a shell/container that pulls from the `GalleryPhotos` collection; no reason to have multiple. |
| 4 | **Konkretna usługa** (template) | **Custom collection** (`services`) | N services exist (sesja kobieca, ślubna, biznesowa, rodzinna, ciążowa…), each gets its own URL `/oferta/[slug]` and admin row. |

| 7 | **Polityka prywatności** | **Custom collection** (`legal-pages`) | Reusable template: polityka prywatności + regulamin + polityka cookies — 2-4 documents, same schema, different slugs. Minimal but genuinely N-of-a-kind. |

**Summary**: 2 custom collections for actual data (services, case-studies), 1 for legal templates, 1 for contact submissions, 1 for photos — and 4 Globals for the singleton pages. The `Pages` collection becomes a fallback for any future one-off page not modelled above (or you delete it if everything is covered).

## 2. Per-page Detail

### 2.1 Strona główna → Global `Homepage`

**URL**: `/`
**Routing**: `src/app/(frontend)/page.tsx` fetches `payload.findGlobal({ slug: 'homepage' })` directly — no slug lookup.

**Structure**: Flat top-level fields for the hero (predictable, always-present), then a `layout` blocks array for all sections below it. This hybrid (flat hero + blocks) is deliberate: the hero is LCP-critical and must always exist, so don't let an editor accidentally delete it via the block list.

| Section (Figma) | Payload approach | Block slug | Primary editable fields |
|---|---|---|---|
| Hero / Navbar | Flat fields on Global | — | `heroImage` (upload→media), `heroHeading` (text), `heroSubtitle` (text), `heroCTALabel`, `heroCTAHref` |
| Intro / O mnie cytat | Block in `layout` | `HomepageIntroBlock` | `heading`, `body` (richtext), `portraitImage`, `quote` (text) |
| Karty usług (wyróżniki) | Block in `layout` | `ServiceHighlightsBlock` | `heading`, `items[]` (relationship → `services`, select up to 6) |
| Kroki do realizacji #1 | Block in `layout` | `ProcessStepsBlock` | relationship → `ProcessSteps` Global, or inline `steps[]` array |
| Galeria (portfolio preview) | Block in `layout` | `GalleryPreviewBlock` | `heading`, `photos` (relationship → `gallery-photos`, hasmany, up to 12) |
| Kroki do realizacji #2 | Block in `layout` | `ProcessStepsBlock` | same block slug reused with different data (two separate block instances) |
| Opinie / Testimonials | Block in `layout` | `TestimonialsBlock` | `heading`, `testimonials` (relationship → `testimonials`, hasMany) |
| Sekcja Proces (dekoracja) | Block in `layout` | `ProcessDecoBlock` | `heading`, `body` (richtext), `decorativeImage` — mostly static SVG |
| Instagram | Block in `layout` | `InstagramBlock` | `heading`, `instagramHandle` (text) — feed pulled client-side or via ISR |
| CTA-section | Block in `layout` | `CTASectionBlock` | `heading`, `subheading`, `ctaLabel`, `ctaHref` |
| Footer + Newsletter | Separate Global | — | see Globals section |

**Linkage**: `ServiceHighlightsBlock` → relationship to `services` collection. `GalleryPreviewBlock` → relationship to `gallery-photos`. `TestimonialsBlock` → relationship to `testimonials`.

**URL**: `/[slug]` (e.g. `/polityka-prywatnosci`, `/regulamin`, `/polityka-cookies`)
**Routing**: handled by the existing `[slug]/page.tsx` — OR better, a dedicated `src/app/(frontend)/[slug]/page.tsx` that checks `legal-pages` before `pages`. Alternatively, a dedicated route group `(legal)`.

**Top-level flat fields**:
- `title` (text, required), `slug`
- `sections[]` — array of `{ sectionTitle: text, sectionId: text (auto-slugified), description: richtext, subsections[]: { title, body: richtext } }`

**Admin**: list columns `title`, `slug`. No draft/publish needed (legal pages update rarely). Versions with max 10.

**Rationale for Collection (not Global)**: there are 3 legal documents (privacy, terms, cookies). A Global would require 3 separate globals. A collection with 3 documents is cleaner and reuses one template. The user controls the slug.

## 3. Custom Collections Needed

### 3.1 `services` — Usługi

- **Why collection**: Multiple services exist (likely 5-8: sesja kobieca, ślubna, biznesowa, etc.), each with its own URL, admin row, and independently editable content. Client adds new service types over time.
- **Fields**: flat identity fields + `layout` blocks (as detailed above)
- **List columns**: `title`, `slug`, `updatedAt`
- **Sortable**: `order` (number field, sidebar) — controls display order on homepage/gallery filter
- **Draft/publish**: yes (can prepare a new service offering and publish on launch date)
- **URL routing**: yes, `/oferta/[slug]`

### 3.2 `case-studies` — Realizacje

- **Why collection**: Photographer adds new case studies over time (one per session shoot). Could be 20+ over a year.
- **Fields**: flat identity + `layout` blocks (as detailed above)
- **List columns**: `title`, `service`, `sessionDate`, `updatedAt`
- **Sortable**: `sessionDate` desc — newest first
- **Draft/publish**: yes
- **URL routing**: yes, `/realizacje/[slug]`

### 3.3 `gallery-photos` — Zdjęcia do galerii

- **Why collection**: Filterable photo library. Photos exist independently of services and case studies — they're the raw portfolio. The Galeria page queries them. Services and case studies reference subsets via relationship fields.
- **Fields**:
  - `image` (upload→media, required)
  - `alt` (text, required)
  - `category` (relationship→`session-categories`, required)
  - `service` (relationship→`services`, optional — for gallery filtered per-service)
  - `caseStudy` (relationship→`case-studies`, optional)
  - `featured` (checkbox) — for homepage gallery preview
  - `order` (number, sidebar)
- **List columns**: `image` (thumbnail), `category`, `service`, `featured`, `order`
- **No draft/publish** — photos are either in or out; simpler without drafts
- **URL routing**: no — library only, queried by other pages
- **Admin ergonomics**: bulk-upload friendly; thumbnail column essential

### 3.4 `session-categories` — Kategorie sesji

- **Why collection**: Taxonomy that `gallery-photos`, `services`, `case-studies` all reference. Editors add/remove categories (e.g. adding "Chrzest" as a new category). Drives the 5 filter pills on Galeria.
- **Fields**: `label` (text, required), `slug` (auto), `order` (number)
- **List columns**: `label`, `slug`, `order`
- **No draft/publish** — categories are always live
- **URL routing**: no — but could eventually have `/galeria/[category]` filtered routes
- **Premature complexity warning**: if the client guarantees exactly 5 static categories forever, this could be a hardcoded enum in `gallery-photos.category`. But a collection is safer for admin control.

### 3.5 `testimonials` — Opinie

- **Why collection**: Testimonials appear on the Homepage, Services, and Case study pages — referenced via relationship fields from multiple places. They are added/removed by the client. Count: unknown from Figma, but the pattern (`slider/grid`) strongly implies N items.
- **Fields**: `authorName` (text), `authorRole` (text, optional, e.g. "Mama Marysi"), `body` (richtext), `rating` (number 1-5, optional), `service` (relationship→`services`, optional — for filtering per-service), `publishedAt` (date), `featured` (checkbox)
- **List columns**: `authorName`, `service`, `featured`, `publishedAt`
- **No versions needed** — simple create/edit/delete
- **URL routing**: no

### 3.6 `faq-items` — FAQ

- **Why collection**: FAQ appears on Galeria, Services (all instances), and Kontakt — referenced from multiple places. Questions are reusable (same Q about pricing on multiple service pages). N items.
- **Fields**: `question` (text, required), `answer` (richtext, required), `category` (relationship→`session-categories`, optional), `order` (number)
- **List columns**: `question`, `category`, `order`
- **No draft/publish, no URL routing**

### 3.7 `contact-submissions` — Zapytania

- **Why collection**: storage for form submissions. Read-only for the admin. Standard Payload forms pattern.
- **Fields**: `name` (text), `email` (email), `phone` (text), `sessionType` (text, from selected pill), `message` (textarea), `gdprConsent` (checkbox), `submittedAt` (date, auto)
- **List columns**: `name`, `email`, `sessionType`, `submittedAt`
- **Access**: `create: anyone`, `read: authenticated`, `update/delete: authenticated`
- **No draft/publish, no URL routing**

### 3.8 `legal-pages` — Strony prawne

Described above in section 2.7.

## 4. Globals Needed

### 4.1 `Homepage` — Strona główna

- **Why Global**: There is exactly one homepage. No list view, no slug management, no "create another one". A Global removes all that cognitive overhead from the admin and from the Next.js routing code.
- **Versions**: yes — `drafts: { autosave: true }` — the client will want to preview homepage changes before publishing
- **Fields**: flat hero fields + `layout: blocks` (as detailed above)

### 4.2 `AboutPage` — O mnie

- **Why Global**: one photographer, one About page. Same reasoning as homepage.
- **Versions**: yes, draft/publish

### 4.3 `GalleryPage` — Galeria (shell)

- **Why Global**: one gallery index. The page shell (hero heading, intro copy, CTA section) is singleton config; photos come from the `gallery-photos` collection.
- **Versions**: yes (for editing intro copy, changing the CTA)

### 4.4 `ContactPage` — Kontakt

- **Why Global**: one contact page, fixed layout, no slug. The form configuration (session-type pills, accordions) is singleton data.
- **Versions**: yes (client may want to update session types, preview before saving)

### 4.5 `Navigation` — Nawigacja

- **Why Global**: the navbar appears on all 7 pages. Its link structure is singleton.
- **Versions**: recommended (nav changes are high-impact, preview before publish is valuable)
- **Fields**: `logo` (upload→media), `links[]` — array of `{ label: text, href: text, isExternal: bool }`, optional `ctaLabel`, `ctaHref` for the sticky CTA button in navbar

### 4.6 `Footer` — Stopka

- **Why Global**: appears on all 7 pages.
- **Versions**: yes
- **Fields**: `newsletterHeading` (text), `newsletterPlaceholder` (text), `columns[]` — array of `{ columnTitle, links[]: { label, href } }`, `socialLinks[]` — `{ platform, href }`, `copyrightText` (text), `legalLinksFooter[]` — auto-populated from `legal-pages` or manual

### 4.7 `SiteSettings` — Ustawienia globalne (optional, discuss)

A catch-all Global for: site name, contact email (used by form handler), Instagram handle, default OG image, Google Analytics ID. Avoids scattering singleton config across multiple globals. **Recommend creating this** — it's a natural home for data that doesn't fit the page Globals above.

**Fields**: `siteName`, `contactEmail`, `instagramHandle`, `instagramUrl`, `phoneNumber`, `address` (richtext), `defaultOgImage` (upload→media)

## 5. Cross-cutting Concerns / Non-obvious Decisions

> **This is the section the user cares most about — explicit calls for review.**

### 5.1 Recurring sections — ProcessSteps, Testimonials, Instagram, CTA-section

These appear on 3-4 pages each. Two viable approaches:

**Option A (recommended by plan agent): Shared blocks that read from Globals/Collections**
- `ProcessStepsBlock` renders steps from `SiteSettings` or its own field. Each page's block instance has no configurable content — it just renders the global process. **Pro**: single source of truth, change once. **Con**: can't have page-specific step wording (e.g. service page might want "Sesja → Edycja → Dostawa" not the generic 4 steps).
- Recommendation: store `processSteps[]` on the `SiteSettings` Global, but allow the `ProcessStepsBlock` to optionally override with inline steps. This gives global default + per-page override in one field.

**Option B: Block-as-File with duplicated content** (current project convention)
- Each page's block instance is independent. Client edits each separately. Safe but creates content drift.

> ⚠️ **Tension with project rule**: We have a HARD rule in `figma-block-generator.md` that blocks are 100% independent (no cross-block imports, no shared helpers). Option A doesn't strictly violate that (a block reading from a Global is reading from a *data source*, not from another block), but it does change the mental model. **Decision needed from the user**: stay strict (Option B, accept drift) or pragmatic (Option A, shared sources of truth via Globals)?

### 5.2 SEO — per-page vs global defaults

Currently: `seoPlugin` adds `meta` tab to `Pages` collection. Decision required:

- Keep `seoPlugin` attached to `services`, `case-studies`, `legal-pages` collections — those are URL-routed, each needs its own meta.
- For Globals (`Homepage`, `AboutPage`, `GalleryPage`, `ContactPage`): add the `seoPlugin` to each Global too — Payload 3.x supports this natively via `globals` array in seoPlugin config.
- Add a `defaultOgImage` + `defaultMetaDescription` to `SiteSettings` Global — used as fallback when page-level SEO is empty.

**The `generateTitle` function in `plugins/index.ts`** currently only handles `Page` type — will need to be extended for each Global and collection added.

### 5.3 Header navigation — Global vs hardcoded in layout.tsx

Currently `layout.tsx` has no Header component at all. Decision: **Global, not hardcoded**.

Hardcoding the nav means a code deploy every time the client wants to add a menu item. A `Navigation` Global with a `links[]` array is worth the small overhead. The `<Header>` component becomes a server component that `findGlobal({ slug: 'navigation' })` inside `layout.tsx`. This is the standard Payload CMS pattern.

**Risk flag**: `nestedDocsPlugin` is currently configured only for `pages` — if you want nested nav URLs auto-built, it's already there. For manual links in `Navigation` Global, just use text href fields.

### 5.4 Footer — Global vs hardcoded

Same answer: **Global**. The newsletter section especially benefits from CMS control (the photographer may want to change the CTA text seasonally).

### 5.5 Instagram integration strategy — needs a decision

The Instagram feed appears on Homepage and O mnie. Options:
1. **Graph API with token** — real-time or ISR-cached. Token expires every 60 days unless refreshed with a long-lived token setup. Maintenance burden.
2. **Manual `instagram-posts` mini-collection** in Payload — photographer uploads 4-6 "highlight" images. Simple, no auth, but not real-time.
3. **Third-party embed** (SnapWidget, Elfsight) — zero maintenance, but external JS.

**Recommendation for this portfolio**: manual mini-collection approach (Option 2). Photography portfolio doesn't need live IG sync. A collection `instagram-highlights` with `{ image, caption, postUrl, order }` is 15 minutes of Payload work and zero operational risk. The `InstagramBlock` just queries this collection.

**Flag**: If real-time IG is a firm requirement, note it now — it will need a cron job or webhook revalidation.

### 5.6 Pages collection — keep or remove?

The existing `Pages` collection is currently used as the routing catch-all (slug-based lookup in `[slug]/page.tsx`). With Globals covering Homepage, About, Gallery, Contact and dedicated collections covering Services, CaseStudies, Legal, the `Pages` collection becomes unused.

**Recommendation**: do NOT delete it yet. Keep it as an escape hatch for one-off pages (e.g. "Cennik" landing, "Dziękujemy za wiadomość" confirmation page). But stop using it for the 7 Figma pages — those all have better homes.

If after implementation there are zero Pages entries, revisit and remove. Removing it now risks painting yourself into a corner.

### 5.7 Reviews (`testimonials`) — collection vs hardcoded array

The Figma shows a slider with ~3 testimonials on the homepage, ~3 per service. A **collection is the right call here** (not a hardcoded array and not a premature complexity trap) because: (a) the client will accumulate real testimonials over time, (b) testimonials appear in multiple contexts with filtering by service, (c) the admin UI for adding/removing client reviews is genuinely useful. Keep it simple — no draft/publish on Testimonials.

### 5.8 FAQ — collection vs per-page accordion

FAQ appears on Galeria, all Services, and Kontakt. Same question as above: **collection is correct**. Questions like "Jak długo trwa sesja?" appear identically across multiple service pages. A `faq-items` collection lets the client update the answer once and have it reflected everywhere. Per-page `accordionItems[]` arrays would create content drift across 5+ service pages.

### 5.9 `ProcessSteps` — Global field or standalone collection?

The Kroki do realizacji appear on Homepage (twice), O mnie, all Services, all Case studies. Steps look identical across pages from the Figma. **Recommendation**: store them as `processSteps[]` on `SiteSettings` Global, not as a collection. A collection of 4 step documents is unnecessary complexity. The array field on the Global is sufficient.

**Exception**: if Services need radically different process steps (e.g. "sesja ślubna" has 6 steps, "newborn" has 3), then per-service override via the `ProcessStepsBlock`'s inline array is the right escape valve.

### 5.10 Locale-readiness

The design is Polish-only. However, flag for future: Payload 3.x `localization` is additive but requires schema changes when enabled later. To make future i18n non-painful:

- All user-facing text fields should avoid `localized: false` assumptions
- Don't add `locales: ['pl']` now (it would make every field a localized field even when you don't need it)
- Do note which fields are candidates: `title`, `body`, `heading`, `ctaLabel` — all of them. Fields that should NOT be localized: `slug`, `order`, `image`, `publishedAt`

**Concrete action**: document this decision in a comment in `payload.config.ts`. When/if `localized: true` is added to config later, Payload will migrate the DB automatically.

### 5.11 `nestedDocsPlugin` — currently on `pages`, expand?

The plugin is installed and configured for `['pages']`. For `services` at `/oferta/[slug]` and `case-studies` at `/realizacje/[slug]`, you don't need nested docs (these are flat, one-level collections). The plugin is not needed on them.

For `legal-pages` at `/[slug]` (same level as pages), same applies.

Leave `nestedDocsPlugin` on `pages` only, or remove it if `Pages` collection is eventually retired.

### 5.12 Premature complexity traps to avoid

- **Do NOT create a `PricingPackages` collection** (separate from `services`). The Figma shows 3 packages per service. They don't exist independently — package rows are always in context of one service. Keep them as `packages[]` array inside the `PricingBlock`. A collection would be premature.
- **Do NOT create a `ProcessSteps` collection** (4 documents is not a collection use case — use Global array)
- **Do NOT create a separate `BlogPosts` or `Portfolio` collection** unless the client explicitly asks — the analysis file mentions nothing of the sort
- **Do NOT add back deleted Payload template collections** (Posts, Categories, etc.)
- **Do NOT create `instagramPosts` from the Graph API** without confirming this is a real requirement — manual highlights are sufficient
- **`sessionTypes` in Kontakt**: do NOT make this a collection. The 7 pills ("Newborn", "Ślubne", etc.) are static-ish config, perfectly fine as `sessionTypes[]` array on the `ContactPage` Global. A collection of 7 documents would be extreme overhead.

## 6. Suggested Implementation Order

The ordering principle: build foundations that many later entities depend on, then build Globals (simpler, no routing), then collections with routing.

### Phase 0 — Core infrastructure (unblock everything)

1. **`SiteSettings` Global** — `siteName`, `contactEmail`, `instagramHandle`, `processSteps[]`, `defaultOgImage`. Creates the dependency base.
2. **`Navigation` Global** — `links[]`, logo. Unblocks layout.tsx Header work.
3. **`Footer` Global** — newsletter text, columns, social links. Unblocks layout.tsx Footer work.
4. Register both in `payload.config.ts` globals array.
5. Build `<Header>` and `<Footer>` server components in `layout.tsx` — they become live across all pages immediately.

### Phase 1 — Taxonomy (unblocks photo library)

6. **`session-categories` collection** — minimal (label, slug, order). Needed before `gallery-photos`.
7. **`gallery-photos` collection** — the photo library that GalleryPage and Services both reference.

### Phase 2 — Singleton pages as Globals (deliver visible pages fast)

8. **`ContactPage` Global** — simplest page (flat fields, fixed layout, no blocks). Also creates `contact-submissions` collection at the same time.
9. **`GalleryPage` Global** — shell fields + a few blocks; actual photos come from Phase 1.
10. **`AboutPage` Global** — biographical content, no external dependencies except Media and `processSteps` from SiteSettings.
11. **`Homepage` Global** — most complex, references Services and GalleryPhotos (now available from Phase 1 & below).

### Phase 3 — Shared data collections (enable relationship fields)

12. **`testimonials` collection** — needed by Services and Homepage blocks.
13. **`faq-items` collection** — needed by Services, GalleryPage, and ContactPage.

### Phase 4 — Routing collections

14. **`legal-pages` collection** — low complexity, delivers Privacy/Terms pages.
15. **`services` collection** — most complex collection. Block builder with PricingBlock, ChecklistBlock, etc. Each block needs its `figma-block-generator` invocation.
16. **`case-studies` collection** — MosaicGalleryBlock is the special piece.

### Phase 5 — Blocks registration

For each collection/Global that uses blocks, the `figma-block-generator` is invoked in this priority order for block slugs shared across pages (so they're built once):

**Universal blocks** (invoke first, used in 3+ places):
- `ProcessStepsBlock` (Homepage ×2, AboutPage, Services, CaseStudies)
- `TestimonialsBlock` (Homepage, Services, CaseStudies)
- `CTASectionBlock` (Homepage, AboutPage, Services)
- `InstagramBlock` (Homepage, AboutPage)
- `FAQBlock` (GalleryPage, Services, ContactPage)
- `GalleryPreviewBlock` (Homepage, Services)

**Service-only blocks** (invoke second):
- `ServiceIntroBlock`, `PricingBlock`, `ChecklistWithAccordionBlock`, `AboutPhotographerBlock`

**CaseStudy-only blocks** (invoke third):
- `StoryBlock`, `NarrativeBlock`, `MosaicGalleryBlock`, `CaseStudyCTABlock`

**Page-specific blocks** (invoke last):
- `HomepageIntroBlock`, `ServiceHighlightsBlock`, `StatsBlock`, `ValuesBlock`, `FullWidthImageBlock`, `ImageWithListBlock`, `PolaroidGalleryBlock`, `CTAInfoBlock`
